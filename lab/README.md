# Lab

The lab runs the original Haxial KDX programs in sandboxes on a Linux machine
and records their traffic. It is the evidence behind every protocol claim and
the other half of every differential test.

## Machine

Ubuntu 22.04, reachable only from the maintainer's workstation. One-time root
setup is `lab/setup.sh`; everything after that runs as the unprivileged user
`openkdx`, who is also the self-hosted GitHub Actions runner labelled `lab`.

Layout under `/home/openkdx`:

| Path | Holds | In git? |
|---|---|---|
| `openkdx-src/` | a clone of this repository | — |
| `haxial/bin/` | the Haxial archives from `lab/MANIFEST.txt`, each unpacked beside it | **never** |
| `haxial/tables/` | `kdx.bin`, `hgc.bin` (challenge tables) | **never** |
| `haxial/legacy/` | the maintainer's old server and client directories, `.hap` files, sound lists | **never** |
| `haxial/lab.env` | the lab admin login and the fixed, published password `openkdx-lab` | no (regenerated by `kdx-lab env`) |
| `lab/run/<component>/` | working directories and logs of running sandboxes | no |
| `captures/` | `*.pcapng` and `*.md` scenario notes; copied into `captures/` in the repo by hand | yes, after review |
| `actions-runner/` | the GitHub Actions runner service | — |

## Scripts

| Script | Runs as | Does |
|---|---|---|
| `lab/setup.sh` | root, once | installs i386 libs, Wine, bubblewrap, dumpcap, tools; groups; directories; rustup for the lab user |
| `lab/fetch-binaries.sh` | openkdx | downloads and verifies every archive in `MANIFEST.txt`, unpacks it, extracts the challenge tables |
| `lab/kdx-lab` | openkdx | starts, stops, and captures the original programs in a private network namespace |
| `lab/ci-smoke.sh` | the runner | the `lab` CI job: proves the sandbox and the original server work |
| `lab/differential.sh` | the runner | the `lab` CI job: `crates/openkdx-client/tests/lab.rs` against Server 1.620 and Tracker 1.110 (16 tests, serial, under 25 connections: the server bans an address after 30 in 300 s) |
| `lab/scenarios/*.sh` | openkdx | the scripted capture scenarios; from Phase 2 most drive the OpenKDX `openkdx` CLI (`use_cli`, `cli`, `cli_run`, `cli_bg` in `lab/lib/scenario.sh`) |

## Admin login

The lab server's administrator account is `admin` with the password
`openkdx-lab`, fixed and published so that anyone can decrypt the committed
captures (the session key derives from it). It protects nothing: the server
only ever listens on the sandbox's loopback.

## The runner and untrusted code

The `lab` CI job runs on this machine, which holds the Haxial binaries and the
maintainer's data. A pull request from a fork can rewrite `ci.yml`, including
the `if:` guard that keeps fork PRs off the `lab` job. Two things protect the
machine, and both must stay in place:

1. **Repository setting**: Settings → Actions → General → *Fork pull request
   workflows from outside collaborators* → **Require approval for all outside
   collaborators**. Nothing from a fork runs anywhere until a maintainer
   approves it. The `if:` guard in the workflow is only a convenience on top.
2. **The runner user has no elevated access**: `openkdx` has no sudo and is
   **not** in the `docker` group (membership there is equivalent to root).
   Docker images for `openkdxd` are built on hosted runners, not here.

## Lock

One lab session at a time. `scenario_begin`, `kdx-lab selftest`,
`lab/ci-smoke.sh`, and `lab/differential.sh` take `~/lab/run/lab.lock` and
refuse if a namespace is already up, so a CI job cannot trample a human
session or record its traffic. `FORCE=1` (scenarios) or `--force` (selftest)
overrides the namespace check. The CI job runs on every push, so the lab is
busy for a minute or two after one; a refused run leaves the running session
alone (its cleanup trap is armed only after the lock).

## Captures with the OpenKDX client

`dumpcap` hands packets over in blocks that close after about a second, so
`kdx-lab capture start` waits for its packet socket and `capture stop` lets
that timeout pass before the SIGINT; a one-shot `openkdx` session is a few
hundred milliseconds and was lost otherwise. The scenario notes get a
`## Client transcript` section from `$RUN/cli.out`.

## Rules

- Nothing from `haxial/` is ever copied into the repository. CI's blocklist
  (`ci/check-blocklist.py`) catches the known hashes; the rule covers the rest.
- Ghidra projects and decompiled output stay on the lab machine. Only our own
  notes and address landmarks are committed.
- A capture is committed together with its `.md` describing the exact steps
  that produced it, so it can be reproduced.
